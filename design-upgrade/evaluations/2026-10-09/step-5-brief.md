# Step 5 — proposed mockup brief

**Prepared for review; mockups have not begun.** [Baseline findings](findings.md) · [39 screen scorecards](README.md) · [Accepted process](../../plan.md)

The objective is a recognizable GTOP product whose composition supports curiosity during learning, focus during practice, and precision during administration. Premium quality should survive real text, populated lists, errors and mobile use. A large hero, dark theme or more motion is not an acceptance criterion by itself.

## Begin with a meaningful test of the direction

Start with **R21 Dashboard**, desktop and mobile, using the baseline’s real information and a returning learner’s context. Show a clear next practice action, useful progress/recent work and the invitation return cue. This tests whether GTOP’s educational character can carry into daily use without consuming the mobile screen with a generic hero.

After that direction is reviewed, test it on **R30 Quiz Summary** and **R09 Question Library**. These are intentionally different jobs: one explains learning, the other handles dense admin content and consequential controls. A direction that succeeds only on a welcoming dashboard is not yet a product-wide direction.

Use the existing public and Plant Lab art as evidence of useful character, not as an obligation to preserve every current color or illustration. Resolve the g/star versus three-bar brand relationship explicitly in the first direction review.

## Deliverable for every screen

- A clearly labeled **proposed desktop image and proposed mobile image**, linked beside the immutable baseline and its rating. Retain actual labels, roles, content density and plausible long text; use synthetic personal data.
- The principal improvement objective, what is preserved, and the decisions about hierarchy, type, spacing, color, imagery and controls.
- Applicable additional frames: selected/active, empty/no-match, loading, saved, failed, missing, dense and confirmation. Match the route’s state list; do not invent irrelevant variants simply to fill a template.
- For meaningful motion: a short storyboard specifying trigger, changing element, purpose, interruptibility and reduced-motion alternative. A still mockup cannot validate timing, scrolling, saved state or responsiveness.
- Review outcome: accepted / revise / unresolved, with dated user feedback. Never infer acceptance from a model score.

Record visual proposals under a new dated `design-upgrade/mockups/` directory on `main`; keep baseline originals unchanged. Link each proposal back to its R-ID and findings. Maintain source/provenance for generated art and distinguish generated concept images from exact-layout references. If image generation cannot preserve exact text or controls, refine the layout in a precise design surface before acceptance.

## Acceptance checks

| Aspect | Required evidence before accepting the affected proposal |
|---|---|
| Identity | The dashboard, practice, lab and admin examples read as related parts of GTOP; subject-specific character is intentional. |
| Attention | The main task and consequence are clear with the actual copy and density. Mobile is composed deliberately; it is not merely a vertical list of desktop sections. |
| Precision | Long questions, title wrapping, labels, status, selection counts and confirmation controls remain readable. No R34/R38/R09-class defect survives. |
| Learning | Selected answer, reasoning and next practice are connected; useful baseline feedback and continuity are retained. |
| Density | A dense register/review/history example is included. Filtering, retrieval and active record context remain understandable. |
| States | Required route variants receive equal care; consequential states are not postponed until coding. |
| Interaction boundary | Unresolved saved/resume, motion, sticky, native-device or accessibility behavior is explicitly carried into a small interactive validation task. Still images do not close these questions. |
| User gate | The user explicitly accepts the direction and then the required screen/state coverage before development starts. |

Use criteria v1.1 for the eventual before/after comparison. An 8+ target is a review aid; no average overrides a major defect or substitutes for user acceptance. Re-score against equivalent evidence after proposals are concrete.

SERVICE-TRUTH ANNOTATION — REFINEMENT V2
4 October 2026 · annotations only; no change to the independent original proposal or frozen visual designs

The renders and handoff contain both supported service behavior and proposed product capabilities. They are a design specification, not evidence that every pictured control exists. This annotation is the implementation authority where a visual concept implies unsupported behavior. Do not ship a control that only looks functional.

VERIFIED FOR THIS DELIVERY

• Authenticated admins can read paper records, conversation history and outputs, and reply, revise and cancel. Preserve current admin-wide access.
• ownerUid is immutable creator attribution. Display Requested by; no reassignment control or creator-only access restriction.
• In-app updates are recipient-scoped. Device push is opt-in. No email promise.
• Output may be an immutable printable HTML artifact. Open paper and browser Print / Save PDF are truthful when wired to the saved artifact. A separate answer key must resolve its own content/print surface; no server-generated PDF-download promise.
• The agent is scheduled every two hours, 08:00–20:00 Asia/Kolkata. The UI can describe the next scheduled opportunity without promising completion or an operational watchdog.

PROPOSED CAPABILITIES — NOT VERIFIED AS IMPLEMENTED

Attach images: the current admin journey has no upload capability. The pictured Attach images button, per-image usage choices, upload progress and replace-image recovery are design requirements only. Omit the button and related upload claims from the delivery until an actual authenticated upload/storage/reference flow exists. Preserve image references already supported by the service; do not invent successful uploads.

Needed by: the optional date/time picker, persisted deadline metadata, deadline-risk computation and deadline ordering are proposed. An admin can describe timing in natural language using the supported request input, but that alone does not establish a tracked deadline. Do not expose a date picker, calculated deadline badge or priority promise without stored/validated metadata and supported behavior.

Academic/date facets: class, board, subject, chapter and created/completed-date filters in the history concept are intended retrieval features. Only render a working facet when the relevant metadata, query semantics and counts are implemented. Use available supported search/retrieval behavior in the current delivery; do not simulate filtering or imply complete archive coverage from a bounded local list. The 10,482-paper/137-result screenshot is illustrative test content, not a service capacity or query result claim.

Archive: archiving, Include archived and restore are proposed capabilities. Omit them until durable state and retrieval semantics exist. Never substitute deletion for archive or hide a record locally while claiming a persistent archive.

Structured clarification choices: the two radio answers demonstrate the desired clarification UX, but structured choice generation/handling is not verified. The supported fallback is to display the actual clarification text and accept a natural-language reply. Do not invent radio choices or suggest the service generated them. Only offer choices if their semantic answers are real and submitting them uses the supported reply action. Retain explicit Send answer and preserve draft reply text on failure.

One-click Try again: there is no implemented retry/watchdog service. The failure screenshot's Try again button is a proposed requirement, not an existing endpoint. Do not show a nonfunctional retry action or promise automatic retry, recovery attempts or stale-job detection. Use a verified existing action only when it truly resumes work, and label its actual behavior accurately. Otherwise retain the request/history and show the failure plus currently supported request/reply/revision actions; do not claim retry is available.

Preserved drafts: draft persistence and its scope must be verified. Do not claim Saved, private server storage or cross-device continuity from an unsaved local textarea. “Draft · not submitted” avoids that claim. If local persistence is implemented, say “Saved on this device.”

OTHER DELIVERY RULES

• All pictured example statuses, attribution, counts, attempts and artifact previews are synthetic design evidence. Production labels must bind to actual service state.
• The core selected architecture remains useful with supported functionality: one durable Papers register, direct natural-language request/reply, observable asynchronous status, immutable completed artifacts and distinct active revision context.
• Unsupported pictured capabilities should remain explicit backlog/design intentions. Do not add disabled or decorative facades merely to match the mockup.
• A completed output remains readable when a new request is pending; preserve existing stored content. The actual version/revision object and actions must map to implemented service semantics rather than assume a new backend model.

PAPER REGISTER — SELECTED-DIRECTION REFINEMENT
Refinement v2 · implementation handoff · 4 October 2026

The original independent proposal remains unchanged. This addendum refines its selected paper-register structure using independent review and verified service facts. It supersedes the original proposal's server-PDF, email and reassignment assumptions for this delivery.

VERIFIED SERVICE CONTRACT

• All authenticated admins can read paper records, conversations and outputs, and can reply, revise and cancel. Preserve that existing access policy. Do not introduce creator-only access or new tenancy.
• ownerUid is immutable creator attribution. Display “Requested by”, not an assignable Owner. There is no Change owner action. “Requested by me” is a retrieval filter, not an access boundary.
• In-app notifications belong to their recipient. Optional device push requires opt-in and actual permission/registration. Do not promise email. Permission denial must not block paper creation or hide in-app updates.
• Completed output may be an immutable printable HTML artifact. Use Open paper and Print / Save PDF. Do not imply a server-generated PDF download. The answer key remains a distinct immutable artifact and a distinct print action.
• Scheduled runs remain 08:00, 10:00, 12:00, 14:00, 16:00, 18:00 and 20:00 India time (Asia/Kolkata, UTC+05:30). Show next opportunity, not promised completion. Never invent progress, delivery success, draft persistence or automatic retries not confirmed by the implemented service.

MOBILE INDEX

Keep one Papers screen and one New paper action. All papers, Needs action, In progress and Ready are filters over the same permanent paper records. On phones, render all four in a 2×2 grid with at least 44px hit targets. Ready is always visible; no hidden horizontal tab or overflow discovery is needed.

Search is full width. Below it place the Requested by selector (Everyone / Requested by me) and Filters. Preserve text, active filters, sort and scroll on return from a record. Use real scoped counts or omit them; never reuse unrelated/global counts in filtered search.

Show every action-needed record in the ordered result set. A summary such as “2 papers need action · both shown first” describes the actual loaded example, not a limit of two. At scale the Needs action view must paginate all matching records; do not promote one request and hide the rest.

Compact record order: academic title and stable paper ID; exact state; short next step; creator/deadline. Give one named action: Reply, Recover or Open. For a clarification, put the actual question on the record: “Should this paper total 40 or 44 marks?” A “Needs input” badge alone is insufficient. Failed records describe what failed and that the request is retained.

Completed and active revision are separate lines. Example: “Version 1 ready” with Open, then “Revision 2 queued · 12:00 IST” with View revision. The primary Open action keeps accessing the existing completed output; the revision link goes to its active request. A completed version keeps the paper in Ready even when another revision is running.

The sample mobile records are approximately 142–149px high at 390px width, compared with the much taller initial cards. Both action-needed records remain within the first 844px viewport. Long titles may wrap; do not truncate the information needed to distinguish similar papers. Do not force a large thumbnail or standalone decorative status area into every record.

CURRENT TASK DETAIL

Detail hierarchy: Back to Papers → stable ID and academic title → Requested by / Needed by → useful current task → request details → activity. No history traversal is required before answering.

Clarification shows the full question, why it was asked, complete options and Write another answer. Do not preselect an option. Send answer becomes available after a selection or nonempty free-text answer. Record the meaningful answer under the exact request revision. Preserve text on error; a stale concurrent reply must show the accepted newer answer rather than overwrite it. The next opportunity is supporting text below the action.

At 390×844, the example's Send answer button begins around y=548 and is 44px high; the question and both options appear before it. The remaining original request and activity begin below this action. That is the required hierarchy, not a claim of measured user comprehension.

FIRST REQUEST

New paper has one natural-language textarea labelled “What should the paper include?”, Attach images, optional Needed by/time in IST, and Submit request. Examples are placeholders, not prefilled requirements. Each attachment distinguishes Include in paper from Reference only. Show upload progress/failure against the actual file.

The schedule explanation sits before Submit request. Explain that the admin can leave after the server acknowledges submission and will receive in-app updates. Offer optional device notifications after useful context, not as an initial blocking permission prompt. Label an unsubmitted request Draft; claim Saved only after real persistence, and qualify “on this device” if that is the implemented scope. Do not imply cross-device or private server drafts unless implemented.

READY OUTPUT AND ACTIVE REVISION

Use a dedicated “Version 1 · ready to print” section with a completion timestamp. Question-paper actions: Open paper; Print / Save PDF. Answer-key actions: Open key; Print key. The answer key must be visually and functionally separate from the student paper. State that Save as PDF is a browser-print option, not a generated download.

Print / Save PDF resolves the selected immutable version and opens the browser print flow when the artifact/assets are ready. If direct print is unavailable or blocked, Open paper remains the fallback. Print key resolves the separate key artifact and its own print DOM. Never print a combined page that accidentally includes the answer key. Labels, preview, artifact ID, version and linked content must match the selected record.

When revision 2 exists, add a compact near-title summary: “Revision 2 queued · Next opportunity today, 12:00 IST” with a jump to View revision request. Below the completed output, render a separate Active request / Revision 2 section with its own Queued state, change request, schedule and Cancel revision. Thus the active revision is discoverable immediately, while version 1's print actions remain available. Cancelling the revision never deletes or hides version 1.

The initial refinement accidentally previewed a geography paper inside the science record; v2 corrects both the preview and science print route to P-1044, Class X Science, Light. The version identity is now consistent.

RETRIEVAL AND RECOVERY

Long-history view shows the query, active academic/date filters, actual matching count, stable IDs, full dates and bounded results with Load more. The example uses five records from a simulated 137-result search across a simulated 10,482-paper archive. These are illustrative data, not live service statistics. Do not add fabricated totals to the real product.

No-results view retains the query and visible constraints. Clear filters removes class/board/date/status restrictions while preserving the query. Clear search clears the query independently. Include archived is explicit. Do not silently broaden or replace the query.

Recoverable failure says what stopped: “We couldn’t finish the printable pages.” It confirms the saved inputs only when true, displays the next actual opportunity, and provides Try again plus Edit request. Retry uses the same paper identity and retained inputs. Do not claim an automatic retry already happened without an actual attempt event. A failed artifact-open action retries access, not generation.

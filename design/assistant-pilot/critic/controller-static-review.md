# Independent controller/domain static review

Requested by parent after rendered UI review. Read-only inspection of `tools/gtop-assistant/src`, `assistant-service/service.mjs`, gateway and domain. **No new inference, experiment, deployment or application edit.** Line numbers refer to the inspected candidate before parent corrections; status below is the finding at inspection, not an assertion that later fixes remain absent.

## Material contract defects

1. **P1 — claimed revision jobs lose operation.** `assistant-service/service.mjs:11` excludes `operation` in `publicJob`; `workerJob:159` spreads that projection and never restores operation. `worker.ts:48–49` therefore cannot detect `revise_paper` and takes the create-complete-paper path rather than the targeted-question schema. Server containment then rejects regenerated untargeted content. Include trusted operation in WorkerJob, separate from public DTO, and test service claim → worker handoff.
2. **P1 — worker failure shape is rejected.** `worker.ts:29` sends `error:{code,message}` to `/fail`; `service.mjs:222` calls string-only `text(body.error,2000)`. The resulting 400 is swallowed, so real errors remain running until lease expiry and are mislabeled worker-disconnected. Align the error contract and test the actual gateway request shape.
3. **P1 — requirement clarification is not retained.** `policy.ts:16–31` ignores `requirementsPatch` and parses only current text against old/default requirements. Replies such as `Hindi`, `Hindi answers` or a bare mark total after a clarification cannot apply the established request. Internal choices can be disabled but not explicitly re-enabled. Add source-identified clarification/requirement provenance, not unchecked model authority.
4. **P1 — whole-paper revisions cannot change requirements.** `domain/index.mjs:59–62` always validates against base requirements, including for an untargeted whole-paper revision. A user-authorized 80→60 mark or answer-language revision cannot pass, though the worker accepts the updated requirements. Keep targeted locks, use new verified requirements for whole-paper revision.
5. **P1 — explicit prohibition can still mutate.** `policy.ts:36` negates only generate/create/बना; line40 forces revision on revise/replace/change. `Do not revise the paper` and `Don't change question 6; explain it` can delegate against user instructions. An explanatory `Why did you change question 6?` also matches. Honor negation/discussion intent before an execution override.

## Additional intent, recovery and publication issues

- **P1/P2 target provenance:** `policy.ts:41–44` accepts a model-chosen question number when no number appears in the user request. Broad revision requests may silently become targeted edits. Require original-text provenance or clarification.
- **P1/P2 task root:** `service.mjs:188` sets new generation's root to the current turn; after clarification the root may be `English please`, with the actual original request preserved only in recent history. Preserve the task root independently of both the latest reply and the conversation's first greeting.
- **P2 section containment:** `domain/index.mjs:72–73` compares section count but replaces all candidate sections with base sections before metadata comparison. A targeted revision can alter section instructions/titles or redistribute unchanged questions without detection. Compare section metadata and ordered question membership.
- **P1/P2 attempt-rule consistency:** `index.mjs:29–30` permits arbitrary printed instructions, while line49 sums every primary question. `Attempt any one question` can contradict a structurally 80-mark paper and still pass. Since only all-required questions plus whole-question OR are supported, the printed attempt rules should come from the trusted structure rather than model prose.
- **P2 canonical publication shape:** `validatePaper` does not assert canonical schema. An object-valued `section.instructions` can render as `[object Object]`, and unknown paper/question fields can persist through the input spread. Shape-validate or whitelist canonical educational content, with storage metadata handled separately.
- **P2 already-aborted signals:** `worker.ts:23` and `adapters.ts:60` add listeners without first checking `signal.aborted`. A stop already delivered before registration can be missed and a child can start. Server delivery fencing is strong, but process consumption still needs an immediate guard.
- **P2 memory consent/history:** `worker.ts:40–41` matches `remember` inside `Do not remember…`; `service.mjs:217` replaces rather than merges previous explicit preferences. Respect negative memory intent and preserve bounded, source-linked prior preferences.
- **P2 aggregate context:** `policy.ts:11–14` bounds only recent user text; root/current requests, profile, question summaries or complete selected question/answer, and current facts sit outside that cap. The model uses 8K context. No actual truncation experiment was run, but aggregate budgeting is not enforced by this implementation.
- **P2 conversational continuity:** `selectContext` removes all assistant messages rather than only untrusted old execution claims. Natural follow-ups to an assistant clarification or explanation lose their referent. Retain relevant conversation as untrusted context while current execution facts remain authoritative.

## Safeguards confirmed by inspection

Original/current requests are UTF-8 hashed and preserved in handoff independently of local interpretation. The server reconstructs history and owner/permission facts. Worker access is bound to enabled identity, owner allowlist and current administrator role; leases and active revision are rechecked before delivery. Student rendering excludes answer fields and escapes model text; KaTeX is strict with `trust:false`. Codex is a fixed direct executable, read-only, with tools disabled and environment allowlisted; pairing material/API keys do not enter its environment. Repairs are bounded and unresolved review issues do not publish.

An initial possible concern about CodeMode diagnostics was **withdrawn**: the adapter ignores item-level diagnostic messages, while only top-level error/turn.failed events fail the run, matching the retained runner behavior. No speculative change was requested.

All findings were sent to parent with paths/lines; parent reported fixes in progress. This document is review evidence, not a claim that bugs were reproduced by running new tests or that the corrected candidate is already verified.

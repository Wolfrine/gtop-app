# GTOP local controller

Node22-compatible TypeScript controller. The installed Node24 runtime also passes local checks. This is a closed educational workflow, not a general shell agent.

Run `npm ci`, `npm run check`, `npm test`. Production uses the PTI native launcher and runner contract v1 (`PTI/tools/local-service-initiator/GTOP-RUNNER-CONTRACT.md`). For an explicitly owned standalone launch use `./start-worker.ps1 -Config F:\Workspace\Support\GTOP\assistant-runtime\worker.json` after confirming that no old or duplicate work can be claimed. The launcher creates a hidden process, checks for duplicates and records its PID/log paths. It does not install a service, alter global environment variables, or change a scheduled task. Keep this PC awake and connected for the private pilot. Inspect `process.json` and the process command line before stopping that controller; never stop unrelated Codex/Ollama or scheduled processes.

The private config contains gateway, workerId, Firebase public apiKey, loopback Ollama URL/model, Codex model (the executable is resolved dynamically) and a private dataDirectory. Production pairing uses `secretProtected`, created with Windows `ConvertFrom-SecureString` under the current Windows user. The server stores only its SHA256. Never commit this file or print the decrypted secret. The private production config lives at `F:\Workspace\Support\GTOP\assistant-runtime\worker.json`; H: retains the existing model weights only. Do not copy Codex authentication files. `codex login status` must say ChatGPT. The CLI child receives an environment allowlist excluding API keys and worker credentials, uses existing subscription authentication, read-only sandbox and disabled tools/plugins. There is no paid-API fallback.

For isolated integration only, a loopback config can use `authEmulator` and `emulatorSecret`. Production endpoints reject that configuration. Local UI's `?emulator=1` is compiled as a localhost-only emulator selection; production fixture code is excluded. No login bypass is shipped.

One persistent Firebase listener watches only minimal assigned-owner dispatch markers. Two independently woken lanes drain local conversation and one Codex paper pipeline; quiet health checks never query the queue. Initial server snapshots, new revisions and reconnects wake both lanes; duplicate revisions coalesce. Network reconnects stay within the SDK, terminal failures back off to 60 seconds, and bearer refresh occurs once per 50 minutes. A main-process atomic worker.lock supplements the existing native role mutex and launcher duplicate checks; after a crash, prove the old PID/native role is stopped before removing a stale lock. transport.json records safe counters for notification, claim, empty claim, job, heartbeat, lease and listener events. Worker heartbeat40s (unchanged90s freshness, one missed publication plus10s network margin), leases120s; stale delivery is refused server-side. Cancellation fences publication immediately; local requests/CLI termination follows the heartbeat within30s. Each Codex stage has a15-minute limit. A worker interruption needs explicit retry; it never automatically reruns an expensive paper. A reviewed retained result is bound to owner, original request hashes, requirements, operation and base hash, then revalidated before retry delivery. Otherwise retry starts fresh.

The model runs on demand. Startup validates runner contract v1 and the current Codex executable. Startup and idle health inspect `/api/tags` for model installation and `/api/ps` for residency; they do not warm Qwen. The active conversation tool loop uses `keep_alive:60` between its calls and an explicit bounded unload in `finally`, including invalid-output and cancelled requests. This owner-authorized request-scoped retention corrects the November 1 per-tool reload regression; the immutable PTI v1 runner document still describes the older per-call zero policy. No follow-up grace is enabled. A process crash has a 60-second fallback expiry, while ordinary completion unloads immediately. The model runner releases RAM/VRAM after a turn. Codex generation/review does not load Qwen; a concurrent chat turn can still use it. Cold replies take longer; the saved task brief, messages, preferences and Codex handoff provide memory across reloads. Exact greetings/thanks use the controller's existing social replies without waking the model. One small outbound listener and the unloaded loopback Ollama dispatcher remain available so remote requests can start work. `ready` requires a server-ready dispatch listener, a reachable dispatcher, the configured model installed, and a resolvable Codex executable; `modelReady` reports actual sampled residency. Unavailable prerequisites report offline and stop new claims. `worker-health.json` retains the safe local reason. The launcher imports TypeScript directly in one Node process, avoiding a separate tsx CLI parent, and runs it at below-normal priority. Its small TypeScript transform helper may also be present.

Private per-job records preserve original server payload, local prompts/raw responses, controller decisions, skill hashes, Codex prompts/schemas/events/results, measured stage durations, validation and delivery. These may contain private conversation content. They remain in the configured private F-drive runtime; repository examples are explicitly synthetic-user integration evidence. No automatic prompt rewriting/training occurs.

Context uses recent relevant conversation, explicit quoted preferences and owned paper data. The entire local prompt plus schema uses a conservative byte budget within8K context, reserving output space. Oversized requests may be represented by a marked excerpt locally; full original text and hashes remain in the Codex handoff. A small-model interpretation never replaces that original. Paper languages differ from conversation language. Legacy saved school/class/lab fields are excluded.

Capabilities are versioned create/revise/explain instructions, pinned syllabus lookup, owned-question lookup, actual status and bounded arithmetic. No arbitrary tool names, shell strings or model-written permissions execute. The gateway supports only create/revise paper work; development, deployment, destructive operations and bank writes are unavailable. Simple paper explanations are local assistance, not independent academic approval.

Current content scope: configured GTOP boards and appropriate programmes, Classes5–12, original practice papers10–100marks (default80), English/Hindi document language. Saved and officially checked curriculum availability differ. Programme/level/code/cohort ambiguity must be resolved; an online check runs only on request. Full syllabus or explicitly selected chapters are supported, covering all topics within those chapters. Attempt every numbered question, with whole-question OR choices only. Section-level selective attempts remain unsupported. Custom mark totals must not be presented as official board formats. Academic acceptance remains with the teacher.

Harness version3 persists a conversation-local task brief and source-message references before a paper exists. It retains selected chapters, all-topic coverage, marks, languages, duration, outstanding clarification and creation hold/resume state. The gateway rebuilds the brief from saved user messages and independently checks any model-selected quotation. Chapter restrictions survive delegation and constrain both the curriculum snapshot and publication validator; switching coverage requires a new paper. A discussion of a board is not a selection, and a paused request cannot resume merely because a scope value is mentioned later.

The local adapter preserves user/assistant message roles, keeps the latest request last, supplies compact controller facts and asks only for reply/action on ordinary turns. Optional chapter extraction includes exact user quotations. Non-thinking conversation uses temperature0.7/top-p0.8/top-k20 and at most700 output tokens in the existing8K window; no model weights changed. Invalid JSON gets one bounded repair with actual prior output. Claimed Codex starts/progress are replaced with controller facts. Exact logs and timings stay private; see the [harness release record](../../docs/ai-assistant/HARNESS_IMPROVEMENTS_2026-10-25.md).

Pairing authorization remains in stable `assistantWorkers` documents. Server-owned `assistantWorkerHealth` holds liveness/model residency, so heartbeats no longer invalidate dispatch-rule dependencies. The REST bodies are unchanged; older 30s workers remain compatible during a rolling release. Health readers use legacy pairing telemetry only until the first dedicated health document exists; malformed health fails closed.

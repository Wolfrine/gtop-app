# Reviewed asynchronous practice invitation

Status: tested invitation contract, disabled pending real player/save integration. No merge or deployment. The target is an enabled working pilot after integration acceptance; this gate is temporary.

This experiment asks whether a small curriculum-specific invitation helps learners start and return to solo practice. Supplied evidence was sparse: 74 CBSE Class 12 attempts from four learners, and 23 Solutions attempts from one learner. It does not establish broad demand, ten users/day, unique acquisition, or growth. No GA reports were read.

## Implemented boundary

Admins use existing Custom Quiz setup to select one board/class/subject/chapter and five questions. Reviewed sharing includes a selectable copy fallback and clear content failure. Public `/practice` reveals scope and revision purpose without reading questions. URLs contain curriculum/count only. Sign-in/profile setup retains practice intent; ordinary learners must match their own board/class, while admins have intentional curriculum freedom. Unsafe or repeated return destinations are discarded before the player: only `/`, `/dashboard`, `/reports`, `/profile`, `/practice`, `/admin` are accepted.

The return offer follows results/review and requires a completed exact attempt plus its server-acknowledged result receipt. Keep stores an account-local 24h card on this device, explicitly described as shown when GTOP is opened. Not now adds no card. Failed consent persistence is visible. Off hides the card only after verified removal; failure keeps the card visible and says it is still saved. There are no browser permission requests, push, background timers, email, SMS, contact lists or public rankings.

The exact pack came from private Library `libfile_0197fc7810cc819185b47ed698d528ea`, version 0, 13,763 bytes. All five supplied SHA-256 fingerprints were recomputed locally. The manifest publishes IDs/scope/fingerprints only. Canonical content is hashed over `[board, standard, subject, chapter, question, options, correctIndex, solutions]`. This is source-backed introductory revision after concepts are introduced, not a mastery diagnostic or human teacher approval. All five source answers are canonical index 0. No bank content is generated or changed.

## Exact durable adapter contract

`practice-invite-session.ts` owns `InvitationAttempt`: schema version, UID, role, attempt ID, entry type (`invitation` or deliberate `invitation-retry`), optional parent attempt, curriculum, reviewed revision, exact ordered question IDs/fingerprints, immutable canonical question/options/explanation snapshots, presented questions with stable option orders and selected answers, current index, first-answer/completion state, acknowledged receipt and consent decision. Tab persistence is separate from ordinary quizzes. Source fingerprints are revalidated without random fallback; reload restores the same ID/order/answers before a new attempt is considered.

`INVITATION_PRESENTATION` must be provided with the reliability branch's existing `presentQuestion`, `restorePresentation`, `validOrder`, and `canonicalIndex` helpers. No second shuffle implementation is supplied. `INVITED_SOLO_READY` remains false until the real combined path passes.

1. The invitation guard fetches the five exact reviewed server documents, captures navigation identity and calls `prepare(scope, sources, safeReturns)`. Preparation creates/restores a candidate without staging source or writing storage. Immediately before `commit(candidate)`, the guard rechecks navigation and account. The service also rejects stale candidate generations/navigation/parent attempts. Cancelled reads leave no global pending source. `pendingRetry` is no longer used.
2. The reliability loader handles `practice=invite` through `current()` BEFORE ordinary retry/random/custom loading. It takes the returned exact attempt/questions/current index and invitation entry type, without calling `presentQuestion` again. It must call `started(attemptId)` only when that source is actually loaded. Completed unsaved attempts go to the current summary for the same save ID, rather than starting another quiz.
3. On actual answer/navigation persistence, call `checkpoint(capturedAttemptId, presentedQuestions, currentIndex)`. At deliberate submission call it with `completed=true` before opening summary. Checkpoints reject changed order/content, wrong attempt, account or role, and already completed attempts. The wrapper captures its attempt ID once; it cannot attribute an old player's click to a new attempt.
4. `result(attemptId)` returns the private immutable invitation payload for the generic `QuizResults` save. Persist it with the ordinary canonical answer summaries and the same attempt ID. The generic saver must include this payload in idempotent equality, server acknowledgement/recovery and ownership checks. It must not silently omit snapshots/provenance.
5. In the generic save success callback, capture UID/attempt identity before awaiting and call `acknowledgeCompletion(capturedAttemptId, resolvedResultId)` only after the actual server acknowledgement. The exact deterministic receipt is `attempt-${encodeURIComponent(uid)}:${encodeURIComponent(attemptId)}`. Optimistic values, late A/B callbacks, account changes and duplicate receipts cannot show an offer. Every active-state/consent mutation invalidates older asynchronous restoration.
6. A current summary reload may call `resumeSummary(capturedInvitationAttemptId)`; it verifies durable identity, account, navigation and generation. Historical reports do not use this offer path. They call `invitationHistory(savedInvitationPayload, reviewedRevisionManifest, presentation)` to restore immutable canonical snapshots and recorded answer order without fetching changed bank content. Preserve reviewed revision manifests needed by historical results.
7. Deliberate invitation retry uses `prepareRetry(capturedCompletedAttemptId, revalidatedSources)` and commits only for its authorized navigation. It creates a new attempt ID, linked parent, `invitation-retry` entry type and empty answers; it never converts a reload into a retry. Parent must wire this intent through existing navigation state, without putting attempt IDs in share URLs. Generic ordinary retries retain their own meaning.

## Evidence and limits

Production build passed with existing bundle/style budget warnings. Module suite: 106 tests; focused invitation suites: 25 tests. The public Chromium matrix contains 24 cases across six projects. WebKit remains unexecuted because its browser asset was absent and mirror downloads timed out.

Actual 1440/390/320 Angular captures cover public, mismatch, empty/error, offer/return, admin copy fallback and Off failure. The original harness aborted all external traffic, including fonts, producing clipped icon-name text; those captures are superseded. Corrected captures allow only the font asset hosts and localhost, wait for font/layout settlement, and confirm Material Icons loaded at all three widths. No product font files changed. Critic separately inspected corrected captures. Touch swipes and visible taps reached all options and Next on baseline main; this does not validate PR57's repaired player. Fixtures suppress production requests/results and simulate acknowledgements.

An offline exact-pack check using actual presentation helpers from PR57's earlier `a8d57bb` passed all five content hashes, canonical scoring indices, same snapshot/answer/order reload, and historical review without bank fetch. It verifies that helper boundary, not the corrected player or server save. Independent QA resolved all review-raised contract findings; critic accepted bounded invitation/admin surfaces. Parent/full-shell/formal Central five-cycle acceptance remains separate.

Hooks distinguish `invite_exposure` (paused/unavailable preview), `invite_open` (reviewed preview), `practice_first_answer`, `acknowledged_completion`, `practice_return_click` and `practice_return` (dedicated source actually started). Clicking does not clear the cue or imply successful navigation/content loading. Payloads contain only stage/time/constant experiment/count and sanitized analytics page location. They add no learner/recipient/question/receipt IDs or scope labels. Existing analytics transport can carry its own identifiers; these are data-minimal hooks, not proven anonymous GA transport, unique-user acquisition or successful growth evidence.
